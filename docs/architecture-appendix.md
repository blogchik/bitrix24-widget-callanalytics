# Architecture appendix — assumptions, open questions, review disposition

## Assumptions

1. The statistics record ID is strictly monotonic with row creation per portal for all telephony providers; a build that ignores >ID/<ID operators is detected at runtime and stops the portal with token_status='filter_unsupported' instead of looping.
2. Statistics rows are not deleted in bulk; a rare deletion shifts at most one offset inside a single batch, absorbed by in-chunk dedupe, upsert and rescan.
3. A user access token issued for portal A is rejected at portal B's client_endpoint, so verification at the stored endpoint defeats member_id spoofing. member_id itself is treated as public data and authorises nothing.
4. Installation is restricted to portal administrators and administrators always have full telephony access, so an admin-proven credential returns the complete history; this is re-verified daily with user.admin.
5. user.admin=true implies full 'Call statistics' visibility; non-admins with 'department'/'any' level see only their own calls in v1 (documented simplification). The statistic.get probe is skipped for admins.
6. member_id is always 32 lowercase hex characters and survives portal renames and custom-domain connection; a rename is recovered by the transport-failure refresh path that re-learns client_endpoint.
7. One refresh exchange at install / self-heal / re-authorize is acceptable under Bitrix24's 'do not refresh excessively' rule; routine opens perform none, and unauthenticated exchange triggers are rate-limited to 5 per 10 minutes per member_id and per source IP.
8. The vendor cabinet allows an 'Event installation handler URL' set to https://b24.texnobus.uz/events/; if not, event.bind at install plus the `event=` body dispatch may still deliver events, and the inferred-uninstall rule guarantees rule-7 cleanup either way.
9. /settings/ is opened like /app/ (iframe POST); the JSON form-builder branch is a fallback.
10. The left-menu item comes from the version-card option and arrives as PLACEMENT=DEFAULT; LEFT_MENU is not bound but is accepted by the router.
11. The BX24 JS SDK requires the original APP_SID/DOMAIN/PROTOCOL/LANG query parameters on the SPA URL; the handoff page forwards Bitrix24's query string verbatim.
12. Browsers execute the handoff page's inline location.replace (no assumption about fragment survival across redirects remains).
13. A separate worker container (same image) is acceptable despite the brief's three-service list; SCHEDULER_INLINE=1 collapses it into api.
14. Basic-plan rate limits apply (2 req/s, burst 50; operating 480 s per 10 min cloud, 420 s on-premise); pacing 500 ms, global concurrency 4, fixed batch of 20 pages, adaptive operating limit floored at 300 s and recovered after 5 clean visits.
15. A 72-hour ID-window rescan (with a persisted rescan_from_id) plus two targeted rechecks up to 30 days captures late-attached recordings, transcripts, votes and comments; edits beyond that are accepted as missed.
16. user.current under user_brief returns TIME_ZONE; fallback installer tz, then UTC. Aggregations run live in SQL over a covering index; custom periods are capped at 366 days.
17. user.get with ADMIN_MODE=true under the portal token returns dismissed users when not filtered by ACTIVE; on an ADMIN_MODE error plain user.get is used.
18. Deal tab = calls linked to the deal's contacts/company, calls whose CRM_ACTIVITY_ID is among the deal's call activities (cap 250 = the handler's 5-page budget), and any row a portal emits with CRM_ENTITY_TYPE='DEAL'.
19. Disk/volume and backup encryption on the Hetzner host is handled by ops; only OAuth and application tokens are application-encrypted; phone numbers stay plaintext for filtering; call_record_url is stripped of credential parameters and never leaves the server.
20. Fully isolated on-premise boxes with a custom auth provider (no refresh token) are out of scope in v1: explicit state page, no database row created or modified. Ordinary on-premise portals refreshing through oauth.bitrix.info are fully supported.
21. Cached calls, employees and crm_contexts are purged on uninstall regardless of data[CLEAN]; CLEAN=1 additionally NULLs rest_log request/response bodies for that portal. portals and portal_events are kept forever.
22. RECORDING_MODE=off until the spike is answered; redirect mode is available only if the captured CALL_RECORD_URL carries no credential.
23. Bitrix24 gates app access at the product level; the app implements only the admin / own / denied split, and Bitrix24's separate 'listen to recordings' right is enforced by proxying non-admin playback with the viewer's own token.
24. The ONAPPUSERREADY system-user credential is deliberately not stored: it carries regular-employee rights, would silently truncate the cache if used, and a stored 180-day token is a liability.

## Open questions for the owner

1. Settings URL contract: iframe POST like /app/ (with which PLACEMENT), or the REST-only OnAppSettings* JSON form contract? Default: iframe POST admin status page; the JSON branch answers a zero-step form and logs the payload in milestone 3.
2. Event handler URL: can the vendor cabinet register https://b24.texnobus.uz/events/, and does ONAPPINSTALL arrive for an interface app? Default: register it; event.bind at install and the inferred-uninstall rule cover the case where it cannot be.
3. Isolated on-premise boxes (no refresh token): accept that they are unsupported in v1 with an explicit state page and nothing stored? Default: yes; safe support needs an ops-pinned endpoint allowlist, which is v1.x work.
4. Permission simplification: accept admin / own / denied? Default: accept for v1; test whether statistic.get silently filters for a Manager-role token and revisit in v1.x.
5. Worker container: fourth compose service or scheduler inside api? Default: separate worker; SCHEDULER_INLINE=1 remains available.
6. disk scope: add it if the spike shows only disk.file.get yields a playable recording? Default: no in v1.
7. rest_log retention and body cap: 7 days / 256 KiB, or the strict 3-day minimum? Default: 7 days, 256 KiB, with bodies wiped for a portal that uninstalled with CLEAN=1.
8. Credential takeover: re-seed only when the chain is dead, older than 120 days, or on an explicit Re-authorize (current), or let any admin open take over? Default: current rule; routine opens perform no OAuth exchange at all.
9. Timezone for 'today' and the heatmap: viewer's TIME_ZONE (current) or one portal-wide timezone? Default: viewer's, installer's as fallback.
10. Backfill UX and period cap: newest-first backfill (~2 h per 500k rows at 20 pages/batch) with a progress banner, and a 366-day cap on custom periods? Default: yes.
11. Phone number display for non-admins: masked or full as in Bitrix24? Default: full.
12. Grace period after uninstall: purge immediately (current) or keep rows for N days? Default: purge immediately; UNINSTALL_GRACE_DAYS (30) applies only to the inferred-uninstall path for portals whose token chain died without an uninstall event.
13. ONVOXIMPLANTCALLEND: bind in v1.x for immediate sync instead of 5-minute polling? Default: polling only in v1.
14. LANG values from kz-region portals: ru, kz or en? Default: fallback map kz->ru, unknown->en; confirm in milestone 3.
15. Employee filter for 'own' users: hidden with a banner (current) or shown disabled? Default: hidden.
16. Optional source-IP allowlist on /events/ from dl.bitrix24.com/webhook/app-world.json: add as defence in depth, accepting that a stale list can reject real events? Default: documented but off; application_token plus the admin proof is the control.
17. Empirical check for milestone 2: does consuming the POSTed REFRESH_ID server-side invalidate the paired AUTH_ID that the iframe keeps using for BX24.getAuth()/session exchange? Record in docs/bitrix24-flows.md; if it does, re-seeding must be moved entirely behind the explicit Re-authorize button.

## Review issues applied

- Endpoint invariant enforced: client_endpoint may be written ONLY from an OAuth refresh response. The 'refresh_unavailable' install branch that derived it from the POSTed DOMAIN is removed; isolated on-premise boxes render /state/unsupported_portal and no row is created or modified (closes the forged-DOMAIN takeover of existing tenants). token_status value 'refresh_unavailable' dropped from the DDL CHECK; this also removes the tick-filter gap where such portals were never synced.
- Credential invariant added: access_token_enc/refresh_token_enc may be written only after user.current + user.admin=true is proven with that token at an OAuth-derived client_endpoint, via a single services/portals.py::store_portal_credential() choke point (lint-enforced). Applies to install, self-heal, re-authorize and every event path; a non-admin token can never become the sync credential.
- portals.token_admin_verified_at added; the worker re-verifies user.admin on the stored token daily and flips token_status to no_stats_permission when it becomes false.
- Event verification ladder rewritten (brief rule 5): if an application_token is stored, constant-time equality is required for EVERY event including ONAPPINSTALL/ONAPPUSERREADY; ONAPPUPDATE is the only event that may replace it and only when auth[access_token] proves user.admin=true at the stored endpoint AND auth[refresh_token] exchanges to the same member_id. Unknown-portal events additionally require the admin proof. Tests added (test_events_auth.py).
- ONAPPUSERREADY tokens are no longer stored: portals.system_user_auth_enc column removed (unused, and a stored 180-day token is a liability); the payload is logged (fully redacted) and discarded.
- Event idempotency: portals.last_event_ts added; events not newer than it, and ONAPPUNINSTALL with ts earlier than install_completed_at, are logged 200 no-ops, so a retried uninstall cannot wipe a fresh reinstall.
- Session JWT is no longer put in a 303 Location header (it would be written to the reverse-proxy access log on every open of every tenant). /app/ now returns handoff.html whose inline script does location.replace(target + '#s=' + jwt), with Cache-Control: no-store; Caddyfile.snippet gains a log filter deleting resp_headers>Location and request query strings; test_no_token_in_headers.py added.
- The handoff URL forwards Bitrix24's ORIGINAL query string verbatim (DOMAIN, PROTOCOL, LANG, APP_SID). Without APP_SID the BX24 SDK cannot reach the parent frame, so BX24.init never fired and fitWindow/openPath/getAuth were inert. middleware.ts now reads DOMAIN/PROTOCOL. Milestone 3 gains an explicit BX24.init/placement.info check on every placement.
- Secret leakage through third-party loggers closed: httpx/httpcore loggers pinned to WARNING, the recursive redaction filter attached to the root handler (regexes for client_secret=, refresh_token=, access_token=, auth=), FastAPI exception handler never logs bodies, and /session/exchange + /portal/reauthorize bodies are explicitly excluded. test_secret_logging.py added.
- Redaction is now a recursive walk masking any key matching /(token|secret|auth|password)/i at any nesting depth, applied to both request and response bodies before every rest_log insert (covers ONAPPUSERREADY data{}, refresh responses, future shapes).
- rest_log rows are written in their own short transaction (and on the exception path before re-raising) so a failed work transaction still leaves the exchange logged, as moderation requires.
- RLS fail-closed write paths fixed: tenant_txn(portal_id) re-issues SET LOCAL app.portal_id for EVERY transaction and is the only way to reach calls/employees/crm_contexts (purge, upserts, /app/ employee and crm_contexts writes included). purge_portal runs in tenant context, pre-counts, aborts with purge_incomplete if the first DELETE affects 0 rows while rows exist, and verifies count(*)=0 before clearing purge_pending. test_purge.py + registry lint extended to raw DML.
- Worker fencing added: portal_sync.sync_generation (bumped by install/reinstall/uninstall) plus lease_owner/lease_expires_at are asserted in every cursor/upsert transaction (UPDATE ... WHERE ...; abort on 0 rows), and all REST calls get a 120 s httpx timeout well below the 5-minute lease. Stops a stale runner re-inserting rows after a purge or clobbering a newer cursor.
- Contiguous-prefix cursor rule: a batch may advance high_id/low_id only across the longest error-free prefix of its commands (head_fetch: any per-command error means stay in 'head' and retry). Removes the permanent 50-row holes a single failed sub-command created. test_cursor.py case added.
- head_fetch made idempotent and now runs for backfill_status IN ('pending','head'), so a crash between its two steps no longer wedges the portal in a state where neither head_fetch nor backfill runs.
- Poison-row hardening: CHECK constraints on Bitrix-controlled values (call_type BETWEEN 1 AND 5, crm_entity_type IN (...)) dropped; crm_entity_type widened to varchar(32), call_failed_code to 32, phone/portal numbers to 128, call_id to 255, crm_activity_id to bigint. Rows are parsed independently and quarantined (portal_sync.rejected_rows + portal_events(row_rejected)); chunks are deduped by bx_id and wrapped in a SAVEPOINT with row-by-row retry. One unexpected value can no longer stall the cursor forever.
- Deal tab now also matches rows a portal emits with crm_entity_type='DEAL' (in addition to crm_contexts entity keys and activity ids).
- Throttle fixed: 429/503 increment a separate throttle_hits counter and never the consecutive_failures breaker; the adaptive operating limit is only lowered when OUR observed operating is within 20% of the limit, is floored at 300 s and recovers to the default after 5 clean visits; next_run_at = operating_reset_at + 60 s; batch_pages halves (min 5).
- batch_pages simplified per the owner's minimality preference: fixed 20, halving under limit errors, restored after clean visits, never doubled to 50.
- Incremental sizing: one probe command first, then pack min(ceil(total/50)-1, batch_pages) further pages, instead of firing up to 50 blind offset commands every 5 minutes on a quiet portal. 'Repeat immediately' capped at 10 loops per visit.
- Filter-honoured guard added: every returned row is asserted against the requested ID filter; a violation sets token_status='filter_unsupported', next_run_at='infinity' and an explicit state page instead of a hot loop against an on-premise build that ignores the operator.
- Rescan lower bound is now the persisted portal_sync.rescan_from_id (high_id observed ~72 h ago, advanced monotonically), and the rescan is skipped when the window is empty - a quiet weekend can no longer turn the hourly rescan into a full-history re-read.
- /install/ on an already-active portal no longer resets cursors: tokens, placements and application_token are refreshed but portal_sync cursors are reset only when the row is new or was uninstalled (a version-update re-run no longer re-imports 500k rows).
- Token re-seed on open is no longer routine: the 'token_user_id == me.ID' branch is removed. Re-seed happens only when token_status != 'ok', when token_refreshed_at is older than 120 days, or on an explicit Re-authorize; at most one exchange per portal per 10 minutes; a failed opportunistic re-seed leaves the credential untouched and only logs refresh_failed. /install/ now explicitly sets token_status and next_run_at.
- OAuth exchange rate limiting added (5 per 10 min per member_id and per source IP) in front of /install/, the /app/ self-heal path and unknown-portal events, so an employee cannot script refresh exchanges against the app's client_id.
- Domain-rename deadlock fixed: a transport-level failure of the /app/ open batch triggers one refresh exchange to re-learn client_endpoint (member_id must match), updates domain, logs domain_changed and retries once; the worker does the same after 3 consecutive transport failures before backing off.
- Recording playback made credential-safe: playback goes through a short-lived signed URL (POST /calls/{id}/play-url -> GET /calls/{id}/record?t=...) because an <audio src> cannot send an Authorization header; non-admin playback proxies with the VIEWER's own token so Bitrix24's separate 'listen to recordings' right is enforced; call_record_url is never returned to the browser, is stored with auth/token/sig query parameters stripped, is excluded from the content-change comparison, and redirect mode is forbidden unless the spike proves the URL carries no credential. §9 updated to test the shipping mechanism.
- CRM tab context hardened: if any CRM command of the open batch errors, the handler renders /state/crm_no_access and mints no entity JWT; crm_contexts rows are written only from a fully successful resolution by the current opener and are served only when resolved_at >= JWT.iat (or resolved by the same sub).
- Fallback uninstall path added for brief rule 7 independence from the unconfirmed events URL: best-effort event.bind('ONAPPUNINSTALL'/'ONAPPUPDATE') at install (result recorded in capabilities), `event=` body detection on /app/, /install/ and /settings/ dispatched to the events handler, and an inferred-uninstall rule (dead token chain + no admin open for UNINSTALL_GRACE_DAYS=30 -> uninstalled + purge_pending + portal_events(uninstall_inferred)).
- CLEAN=1 honoured: portals.purge_bodies is set on uninstall with data[CLEAN]=1 and the purge job NULLs rest_log request/response bodies for that portal (keeping method/status/time rows).
- Dispatch fixed: tick() never awaits sync work and never uses one shared APScheduler job id; portals are dispatched as asyncio tasks under a Semaphore(GLOBAL_PORTAL_CONCURRENCY). portal_sync.run_started_at added so an expired lease without a started run is treated as a dispatch miss, not a phantom crash.
- Dashboard aggregation: calls_portal_start_idx made covering (INCLUDE portal_user_id, call_type, result_group, call_duration, rest_app_id, has_record), summary + per-day + heatmap + per-employee computed in one GROUPING SETS query, custom period capped at MAX_PERIOD_DAYS=366.
- i18n consolidated to one message source: web/messages/*.json and a shared src/i18n/locales.json (locale list + fallback map) are copied into the api image and used by install/handoff/state/error templates; placement TITLE/LANG_ALL are derived from the locale list so adding a language plus a re-bind updates the CRM tab titles.
- Minimality trims per the owner's preference: single encryption key in v1 (envelope key_id kept, no rotation job), system_user_auth_enc removed, statistic.get probe skipped for admins, CRM_ACTIVITY_CAP set to 250 to match the handler's 5-page budget (was inconsistently 1000).

## Review issues rejected

- Make the dl.bitrix24.com/webhook/app-world.json source-IP allowlist MANDATORY on /events/ - rejected as over-engineering for v1: a polled, cacheable IP list is a fail-open/fail-closed liability of its own (a stale list silently rejects real uninstall events), and the now-mandatory application_token compare plus the admin proof already blocks the attack. Kept as documented optional defence in depth and as open question 16.
- Best-effort placement.unbind inside the ONAPPUNINSTALL handler 'to satisfy rule 7 literally' - rejected: the official docs state all API access is revoked at uninstall and the event carries no access token, so the call is guaranteed to fail; adding a doomed REST round trip to a webhook that must return 200 fast buys nothing. Placements die with the app; the real cleanup (mark inactive + purge) is implemented and now also has an inferred-uninstall fallback.
- Drop the portal_events table and log lifecycle to stdout instead - rejected: it is one tiny table that outlives rest_log retention, is where quarantined rows, rejected events, purge_incomplete and inferred uninstalls are recorded, and is the first thing support greps. Removing it would push those signals into rotating container logs.
- Drop the method.get capability probe and the adaptive operating limit - rejected for the probe: it is one command inside a batch that already runs at install and turns a mysterious on-premise sync failure into an explicit state. The adaptive limit was kept but constrained (floor 300 s, only lowered on our own near-limit observation, recovery after clean visits) rather than removed, since on-premise defaults differ from cloud.
- Drop the two-recheck recording budget as duplicated by the rescan - rejected: the rescan only covers the trailing 72 h, while recordings are attached later than that on real portals; the budget is one counter plus one tiny partial index and stops the job paying forever for calls that were never recorded.
- Add record_url_host_path / record_url_kind columns for the recording URL - rejected as premature schema for an unanswered spike: stripping credential parameters at parse time, excluding the URL from change detection and gating redirect mode on the spike result achieves the same safety without columns that may not match the real format.
- Make call_start_date nullable with a fallback for rows that lack it - rejected in favour of quarantining such rows: a row with no start date cannot be placed on any chart or period filter, and a fabricated fallback date would silently corrupt the dashboard the moderator checks.
- Remove the fourth compose service - not applied as a design change; it stays an explicit owner decision (open question 5) with SCHEDULER_INLINE=1 available, because exactly one scheduler regardless of uvicorn worker count is a correctness property, not an extra.
