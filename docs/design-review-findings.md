# Design review findings

Three adversarial reviewers (multi-tenancy/security, sync correctness, brief-and-moderation
completeness) attacked the synthesized design on 2026-09-07. 38 issues: 5 blocker, 18 major,
15 minor. Every issue carries a concrete failure scenario. The disposition of each one
(applied or rejected, with reason) is recorded in `docs/architecture.md`.

---

# Critique 1

**Verdict:** Not sound as written. Coverage of the brief is broad (install page with installFinish, placement.bind before installFinish, single refresh-and-retry, mandated no-access text, REST_APP_ID line filter, client_endpoint for on-premise, 7-day rest_log, ru/en with uz path, fitWindow, metadata-only cache, every listed call field persisted plus the four documented extras), but two paths break numbered rules in demonstrable ways: (1) /events/ verifies ONAPPUPDATE/ONAPPINSTALL/ONAPPUSERREADY with any user's access token instead of the stored APPLICATION_TOKEN, so an ordinary employee can rotate the stored application_token and then fire a fake ONAPPUNINSTALL that wipes the portal cache and sync credentials (rule 5, rule 7, data loss); (2) hard CHECK constraints on Bitrix24-supplied enumerations combined with 500-row chunked upserts and rest_log written in the same transaction turn a single undocumented value (e.g. CRM_ENTITY_TYPE=DEAL, CALL_TYPE=6) into a permanently stalled sync with the failing exchange unlogged. Five further defects must be fixed before milestone 1 ends: a refresh exchange on every open by the installing admin (Bitrix24 blocks apps for excessive refresh), APP_SID/DOMAIN/PROTOCOL/LANG dropped by the 303 redirect (BX24.init never resolves), uninstall handling that depends on a cabinet field the brief does not list with no fallback purge and no best-effort placement.unbind, RLS-fail-closed writes (purge_portal, /app/ employees/crm_contexts upserts) not stated to run under tenant_session so purge_pending can clear with rows still present, and a bearer-only auth model that an <audio src> cannot satisfy for the recording endpoint. Deviations from the brief that the design makes deliberately and should stay surfaced to the owner: storing the refreshed pair instead of the POSTed AUTH_ID/REFRESH_ID (rule 2 literal), ID cursor instead of last_synced_call_start_date, no LEFT_MENU bind, fourth compose service, no placement.unbind. Over-engineering for a 'minimal necessary' v1: adaptive batch sizing, recording recheck budget, system_user_auth_enc, portal_events table, multi-key envelope rotation, capability probe, 30-day crm_contexts purge, per-open statistic probe for admins.

## [BLOCKER] events / rule 5 (APPLICATION_TOKEN verification)
§4.9 rule 2 authenticates token-bearing events (ONAPPUPDATE, ONAPPINSTALL, ONAPPUSERREADY) on a known portal by calling app.info at the stored client_endpoint with auth[access_token], and ONAPPUPDATE then unconditionally REPLACES application_token_enc with auth[application_token]. app.info is callable by any user, and every employee can read their own valid access_token/refresh_token from BX24.getAuth() inside the app iframe. The brief's rule 5 requires comparing APPLICATION_TOKEN against the stored value for ONAPPINSTALL and rejecting mismatches; the design skips that compare on known portals and lets an unprivileged token rotate the secret that guards ONAPPUNINSTALL.

**Failure:** Employee U (non-admin, has app access) opens the app, runs BX24.getAuth() in devtools, gets {access_token, refresh_token, member_id}. U POSTs to https://b24.texnobus.uz/events/ with event=ONAPPUPDATE, auth[member_id]=<real>, auth[access_token]=<own>, auth[application_token]=attacker123, data[VERSION]=99. app.info succeeds (any user) -> handler stores application_token_enc=attacker123, app_version=99. U then POSTs event=ONAPPUNINSTALL with auth[application_token]=attacker123 -> constant-time compare matches -> status='uninstalled', portal tokens wiped, purge_pending=true -> worker deletes every cached call for the portal; admins see 'not installed'. Variant: if token_status!='ok' (e.g. day 181), the same fake ONAPPUPDATE re-seeds sync with U's refresh token; the cache is then rebuilt with U's 'own calls' visibility and the admin dashboard silently shows only U's calls (corrupted cache).

**Fix:** For every event on a known portal: (a) if application_token_enc is stored, require constant-time equality with auth[application_token] FIRST (rule 5), including ONAPPINSTALL and ONAPPUSERREADY; (b) for ONAPPUPDATE, where the token legitimately changes, accept the new value only when the bearer proves elevated identity: run user.admin (must be true) and verify the refresh_token via an OAuth exchange whose member_id matches, AND app.info VERSION must be > stored app_version; store the new application_token only then; (c) never re-seed sync tokens from an event unless user.admin=true for that token; (d) make the dl.bitrix24.com/webhook/app-world.json source-IP allowlist mandatory on /events/ (cached, refreshed every 10 min), not optional. Add tests: employee token + ONAPPUPDATE -> 403; mismatched ONAPPINSTALL -> 403.

## [BLOCKER] schema / sync upsert / rest_log (call data loss)
calls has CHECK constraints on values Bitrix24 controls: crm_entity_type IN ('CONTACT','COMPANY','LEAD') and call_type BETWEEN 1 AND 5. The docs list only those values, but real portals emit undocumented ones (DEAL from calls placed from a deal card, DYNAMIC_*/ORDER on newer builds, new CALL_TYPE codes on on-premise updates). The upsert runs in 500-row chunks with no per-row fallback, and §6 writes the rest_log row 'inside the same transaction as the work'. One bad value therefore aborts the chunk, rolls back the log row, and the cursor never advances; after 10 consecutive failures the portal pauses 6 h and repeats forever. Also, if DEAL does appear, assumption 'DEAL never appears' means the deal tab ignores those rows even when they are the exact calls the moderator expects.

**Failure:** Backfill batch returns 2,500 rows of which row ID 48113 has CRM_ENTITY_TYPE='DEAL' (or CALL_TYPE='6'). INSERT ... ON CONFLICT fails with a check_violation -> transaction rolls back -> the rest_log row for that batch is gone too -> low_id unchanged -> next visit fetches the identical batch -> fails again. consecutive_failures reaches 10 -> portal paused 6 h -> resumes -> same failure. The moderator installs on a portal with such calls: backfill_done freezes at 2,500 rows, 'Importing history' never finishes, and the failing REST exchange is absent from the 3-day log. A rarer variant: a row deleted between two batch sub-commands makes the same bx_id appear twice in one chunk -> 'ON CONFLICT DO UPDATE command cannot affect row a second time' -> same stall.

**Fix:** Drop the CHECKs on crm_entity_type and call_type (keep NOT NULL/format checks only on values we generate); widen crm_entity_type to varchar(32) and treat unknown values as opaque strings shown raw in the UI. Dedupe rows by bx_id in memory before each INSERT. Wrap each chunk in a SAVEPOINT; on any integrity error retry row-by-row, quarantine the offending row into a `sync_rejects` jsonb column/table (or log + skip) and continue, never blocking the cursor. Write rest_log rows in their own short transaction (or after the work transaction) so a failed upsert still leaves the request/response logged. Match the deal tab on crm_entity_type='DEAL' AND crm_entity_id=id in addition to the crm_contexts keys.

## [MAJOR] /app/ open — token re-seed policy (rule 3 / Bitrix24 refresh limits)
§4.4 step 6 re-seeds portal tokens 'if token_status != ok OR token_user_id == me.ID' via a refresh exchange with the POSTed REFRESH_ID. Every open (and every CRM tab open, and every settings open) by the installing admin therefore performs an OAuth refresh. Bitrix24 explicitly warns that renewing 'before every request' or on a schedule gets the app blocked; the design's own decision 11 says refresh only on expired_token. It also bumps token_version and resets next_run_at on each open, disturbing the worker mid-run. Unstated assumption to verify: consuming the POSTed REFRESH_ID server-side does not invalidate the AUTH_ID the parent frame / BX24.getAuth() keeps using for /api/v1/session/exchange.

**Failure:** During moderation the administrator opens the left-menu page, then five deal cards, then reloads the dashboard ten times while checking charts: ~16 refresh exchanges in a few minutes from one IP for one portal. Bitrix24 rate-limits/blocks the app's OAuth client; the worker's next legitimate refresh returns an error -> token_status='reauth_required' -> sync stops for every portal served from that client_id. Secondary: if the refresh invalidates the paired access token, the admin's SPA session exchange an hour later fails with expired_token -> '/state/retry' loop for the installer only.

**Fix:** Re-seed on open only when (a) token_status != 'ok', or (b) the stored refresh token is older than N days (e.g. 120) and the opener is an admin, or (c) an admin explicitly clicks Re-authorize. Remove the 'token_user_id == me.ID' branch. Do not touch next_run_at or token_version on an ordinary admin open. Add a per-portal guard: at most one refresh exchange per 10 minutes outside the worker's expired_token path. In milestone 2, empirically confirm that refreshing the POSTed pair does not kill the AUTH_ID used by BX24.getAuth(), and record it in docs/bitrix24-flows.md.

## [MAJOR] placement handling / BX24 SDK init (brief: iframe must call BX24.init, fitWindow)
§4.4 step 8 answers the Bitrix24 POST with 303 to /dashboard?d=<DOMAIN>&p=<0|1>&l=<lang>#s=<jwt>. The BX24 JS SDK identifies its frame to the parent Bitrix24 page by the APP_SID query parameter (messages are routed as cmd:appSid:params and matched with getAppBySid) and reads DOMAIN/PROTOCOL/LANG from the same query string. The redirect drops APP_SID and renames the other three, so the SPA page has no APP_SID: BX24.init's callback never fires, BX24.fitWindow(), openPath() and getAuth() are inert, and the session exchange (which needs getAuth) cannot work. install.html is unaffected because it is rendered directly on the POSTed URL.

**Failure:** Moderator clicks the left-menu item. Bitrix24 POSTs /app/?DOMAIN=x.bitrix24.kz&PROTOCOL=1&LANG=ru&APP_SID=abc123. Handler 303s to /dashboard?d=x.bitrix24.kz&p=1&l=ru#s=... The SPA loads, injects api.bitrix24.com/api/v1/, calls BX24.init(cb): the parent cannot match the frame (no sid in messages) -> cb never runs -> ready() promise hangs -> layout keeps the skeleton or renders with a fixed short iframe height; charts are clipped, CRM links (openPath) do nothing, and after 3600 s the 401 -> getAuth() returns false -> '/state/retry' loop. Milestone 3 acceptance ('left menu and one CRM tab render') fails.

**Fix:** Forward the original query string verbatim on the redirect: /dashboard?DOMAIN=...&PROTOCOL=...&LANG=...&APP_SID=...#s=<jwt> (keep the exact parameter names; middleware.ts reads DOMAIN/PROTOCOL for CSP). Alternatively render the SPA shell directly from the POST response instead of redirecting. Add a milestone-3 check that BX24.init resolves on every placement and that BX24.placement.info() returns the expected placement. Keep 'never persist APP_SID' as is.

## [MAJOR] uninstall / rule 7 (placement.unbind, mark inactive, delete rows)
Rule 7 is implemented only through POST /events/ (ONAPPUNINSTALL), but the brief's registered cabinet fields are Handler, Install and Settings URLs; the 'Event installation handler URL' is an assumption (A8, open question 2). The design's stated fallback if it cannot be registered is 'uninstall detected only by token revocation and cleanup happens on reinstall', i.e. cached call rows of an uninstalled portal stay in our database indefinitely, and a portal that never reinstalls is never purged. Rule 7's placement.unbind is dropped entirely instead of attempted best-effort. Events posted to /app/ or /install/ (some cabinets deliver lifecycle events to the install URL) would fail the allowlist and render 'bad request'.

**Failure:** Owner cannot register /events/ in the cabinet (or ONAPPUNINSTALL for an interface app is delivered elsewhere). Customer uninstalls with 'Clear application data' = yes. Our worker's next run gets NO_AUTH_FOUND -> token_status='reauth_required', next_run_at='infinity'. Nothing else happens: 250,000 call rows with phone numbers, CRM ids and record URLs remain readable in our Postgres for months. Moderation test 'Uninstalls' has no observable effect on our side, and the brief's rule 7 (mark inactive, delete rows) is not met.

**Fix:** (1) At /install/, additionally call event.bind('ONAPPUNINSTALL', 'https://b24.texnobus.uz/events/') and event.bind('ONAPPUPDATE', ...) with the admin token (research: unconfirmed but cheap; log the result into portals.capabilities). (2) Make forms.py detect an `event=` body on /app/, /install/ and /settings/ and dispatch to the events handler before the placement allowlist. (3) Add a fallback purge policy: when the portal token is dead (NO_AUTH_FOUND/invalid_grant) and app.info via a fresh admin open has not occurred for UNINSTALL_GRACE_DAYS (e.g. 7), set status='uninstalled', purge_pending=true, portal_events(uninstall_inferred). (4) In the ONAPPUNINSTALL handler make one best-effort placement.unbind per CRM placement with the still-stored access token, swallow all errors, then wipe tokens; this satisfies rule 7 literally and covers builds where revocation happens after the event. Surface to the owner that the events URL must be registered in the cabinet.

## [MAJOR] RLS fail-closed write paths (purge, /app/ housekeeping)
Decision 6 makes calls/employees/crm_contexts FORCED RLS with policies bound to app.portal_id, so a statement issued without SET LOCAL app.portal_id sees and affects zero rows. §5.9 defines purge_portal(portal_id) as 'DELETE FROM calls WHERE portal_id = X ... until none, then purge_pending=false' and the tick 'runs in a control session, no RLS'; §4.4 steps 4 and 7 upsert employees and crm_contexts inside the /app/ handler which only says it looked up portals by member_id. Neither path is stated to open tenant_session(portal_id). Because RLS fails closed, these bugs are silent: DELETE returns 0 rows and looks finished; INSERT is rejected or returns 0 rows.

**Failure:** ONAPPUNINSTALL arrives, purge_pending=true. tick() dispatches purge_portal(42) in the control session: DELETE FROM calls WHERE portal_id=42 AND id IN (SELECT ... LIMIT 10000) affects 0 rows (policy predicate NULL) -> loop condition 'until none' is immediately true -> purge_pending=false, portal_events(purge_done). 250,000 rows remain. On reinstall head_fetch/backfill re-upsert over them; if the portal never reinstalls the data persists indefinitely, violating rule 7 while the audit log claims success. Same class: the /app/ handler's crm_contexts upsert for a deal tab silently writes nothing -> every GET /api/v1/calls returns 409 context_missing -> exchange loop -> the CRM tab never renders.

**Fix:** Make tenant_session(portal_id) the only way to obtain a connection in services/calls_repo, services/employees, services/crm_context and sync/purge; have test_registry_lint.py also grep for raw DELETE/INSERT on RLS tables outside those modules. In purge_portal, after the loop, run SELECT count(*) under the tenant context and assert 0 before clearing purge_pending; if the assertion fails, record last_error_code='purge_incomplete' and leave purge_pending=true. Add tests: purge under control session must fail the assertion; /app/ deal open must produce a crm_contexts row readable under portal context.

## [MAJOR] recording playback endpoint / cookie-free auth (milestone 6)
Decision 4 makes the app cookie-free with Authorization: Bearer on every /api/v1/* call, and §9 option 2 / decision 17 expose GET /api/v1/calls/{id}/record behind get_principal to be used as the <audio> source (the spike measures 'seekability in the <audio> element', which only exists when the element streams the URL directly with Range). An <audio src> request cannot carry an Authorization header, so in proxy or redirect mode the request arrives unauthenticated and get_principal returns 401; fetching via fetch()+Blob instead would break Range seeking and buffer whole files in memory, and would not measure what the spike claims to measure.

**Failure:** RECORDING_MODE=proxy after the spike. InlinePlayer renders <audio src="/api/v1/calls/9081/record" controls>. Browser issues GET without Authorization -> get_principal -> 401 -> player shows 'cannot load'. Every recording in the moderator's test fails, and the spike's option-2 numbers (TTFB, seekability, memory) were never actually obtainable through this endpoint as designed.

**Fix:** Add a per-call signed playback URL: GET /api/v1/calls/{id}/record?t=<HS256 token {pid, sub, acc, call_id, exp=now+5min}> minted by GET /api/v1/calls (or a POST /calls/{id}/play-url) under the normal bearer session; the record endpoint verifies `t` only, applies scope_filter (own/all) and the portal status check, sets Cache-Control: no-store, forwards Range/Content-Range. Describe this in §9 so the spike tests the real mechanism. Define now that `redirect` mode is allowed only if the captured CALL_RECORD_URL contains no credential (no auth=/token= parameters); otherwise proxy or off.

## [MINOR] worker tick vs refresh_unavailable state
§4.3 step 2 says isolated on-premise boxes without REFRESH_ID get token_status='refresh_unavailable' and 'sync runs only while the token is fresh', but §5.9 tick selects only token_status='ok'. Such portals are never synced at all.

**Failure:** Isolated box admin installs (REFRESH_ID empty), opens the app: token stored, token_status='refresh_unavailable', token_expires_at=now+3600. tick() WHERE token_status='ok' never picks it; backfill_status stays 'pending' forever and the dashboard shows 'Importing history 0 / ?'.

**Fix:** tick predicate: token_status IN ('ok') OR (token_status='refresh_unavailable' AND token_expires_at > now() + interval '2 minutes'); on every admin open of such a portal overwrite access_token_enc/token_expires_at from AUTH_ID/AUTH_EXPIRES (no refresh).

## [MINOR] i18n / uz-ready structure
Decision 18 claims Uzbek is 'a file drop plus one array entry', but strings live in three places: web/messages/*.json (next-intl), a separate two-locale dict in api/app/handlers/templates for install/state/error pages, and LANG_ALL in placement titles. The backend fallback map is also duplicated from src/i18n/config.ts.

**Failure:** Owner adds uz.json and the config entry; a kz-region user with LANG=uz still sees Russian on install.html and every server-rendered state page, and the CRM tab title stays 'Звонки' until someone re-binds placements. The 'no refactoring' promise in the brief is not met.

**Fix:** Keep one message source: put the handful of server-rendered strings in the same messages/<locale>.json files (mounted/copied into the api image or extracted at build) and load them by the same fallback map exported from a shared JSON; derive placement LANG_ALL from the locale list so a re-bind picks up new languages automatically. Document the three touch points explicitly if they are kept.

## [MINOR] over-engineering vs owner preference 'minimal necessary'
Several mechanisms exceed the brief and milestone 1: adaptive batch_pages (10→50 with halving), the two-recheck recording budget with its own partial index, system_user_auth_enc, the portal_events table, a multi-key AES envelope with rotation/reencrypt(), method.get capability probe and adaptive operating_limit_s, 30-day crm_contexts purge job, a statistic.get probe on every open even for admins (spends shared operating time), and a fourth compose service. Some are internally inconsistent: CRM_ACTIVITY_CAP defaults to 1000 but the handler follows at most 5 pages × 50 = 250 activities; the RESCAN 72 h window plus rechecks duplicates work the rescan already covers for the first 72 h.

**Failure:** Milestone 1 scope grows by roughly a third with no moderation or correctness benefit; a deal with 400 call activities silently loses 150 of them in the tab because the page cap (250) is below the documented cap (1000).

**Fix:** For v1 ship: fixed batch_pages=20, one rescan window, single encryption key (envelope format kept so rotation can be added later), no system_user_auth_enc column, skip the probe when user.admin=true. Either raise the page loop to ceil(CRM_ACTIVITY_CAP/50) or set the cap to 250 and say so. Keep portal_events only if support genuinely needs it; otherwise log lifecycle to stdout. Surface to the owner that these are optional extras.

## [MINOR] uninstall data retention (CLEAN=1) and rest_log contents
rest_log stores full response bodies (phone numbers, CRM ids, record URLs) for 7 days and is explicitly retained after uninstall; ONAPPUNINSTALL data[CLEAN]=1 is only recorded in portal_events, not acted on.

**Failure:** Customer uninstalls with 'Clear application data' checked. The worker purges calls/employees/crm_contexts, but 7 days of raw statistic.get pages with every phone number remain in rest_log.response, contrary to the user's explicit choice.

**Fix:** On ONAPPUNINSTALL with CLEAN=1 (and in purge_portal), also NULL the `response`/`request` bodies of rest_log rows for that portal_id (keep method/status/time_block rows so the 3-day log of the exchange itself survives); document it in moderation-checklist.md.

# Critique 2

**Verdict:** Not ready for milestone 1 in its current form. The design's isolation core (member_id tenant key, forced RLS with fail-closed predicate, JWT-bound portal context, single-flight refresh, AES-GCM envelope with AAD) is sound, but two paths break the stated trust root and must be removed or fenced before any code is written: (1) the empty-REFRESH_ID install branch lets anyone who knows a portal's member_id overwrite that tenant's client_endpoint with an attacker host, turning every subsequent user open into a token-harvesting call and poisoning the cache; (2) lifecycle events are 'verified' with app.info, which any employee's token passes, so a non-admin can replace application_token and forge ONAPPUNINSTALL to wipe the portal, or seed a low-rights token as the sync credential and silently corrupt the cache. Beyond those, fix the JWT-in-Location-header and httpx-URL logging leaks, make purge and every job run under an explicit per-transaction tenant context (otherwise FORCE RLS makes the uninstall purge a silent no-op), forbid portal-token recording playback for non-admins, add a recovery path for domain renames, and stop re-seeding tokens on every installer open. The remaining findings are polish that can land during milestones 3-6.

## [BLOCKER] Trust model / client_endpoint poisoning (§4.3 step 2, refresh_unavailable branch)
The design's trust root is 'client_endpoint is written only from the OAuth refresh response', but the isolated-box branch of /install/ (empty REFRESH_ID) writes client_endpoint = PROTOCOL://DOMAIN/rest/ after 'verifying' AUTH_ID against that same attacker-chosen DOMAIN, and then UPSERTS the portals row by member_id. member_id is not a secret (every app vendor installed on the portal receives it, and any employee can read it from BX24.getAuth()). This re-opens the forged-DOMAIN takeover the design claims to have closed, now against an EXISTING tenant.

**Failure:** Victim portal V (member_id M) is installed and healthy. Attacker POSTs /install/ with member_id=M, REFRESH_ID='', PROTOCOL=1, DOMAIN=evil.example, AUTH_ID=anything. Backend calls https://evil.example/rest/app.info → attacker's server returns {result:{INSTALLED:true}}; step-3 batch (user.current, user.admin=true, method.get, placement.get) is answered by the attacker's server; step 4 overwrites V's row: client_endpoint=https://evil.example/rest/, tokens=junk, token_status=refresh_unavailable, application_token_enc=attacker value, portal_sync reset. From then on every real open of V by any user (POST /app/ from Bitrix24) runs the step-4 batch 'at the stored client_endpoint' with that user's real AUTH_ID → the attacker harvests every V user's access token (admins included) and uses it against V's real REST API (crm + telephony scopes) for an hour per open. The worker also syncs rows from evil.example into V's cache, and the attacker holds V's application_token so can forge ONAPPUNINSTALL.

**Fix:** Enforce the invariant in code: client_endpoint may be written ONLY from an OAuth refresh response (or, for on-prem, from a value operators pin per member_id in config). Remove the refresh_unavailable install branch from v1 (isolated boxes are out of scope) or restrict it to (a) member_id not yet present in portals AND (b) DOMAIN on an ops-maintained ONPREM_DOMAIN_ALLOWLIST; never let an unproven payload touch an existing row. Add a test: POST /install/ with empty REFRESH_ID against an existing member_id must not change any column.

## [BLOCKER] Event verification (§4.9 rule 2) — application_token replacement and forged uninstall
Token-bearing events on a known portal are authenticated by calling app.info with auth[access_token]. app.info is basic-scope and succeeds for ANY user of the app on that portal, and every employee gets their own access token via BX24.getAuth() in the iframe. ONAPPUPDATE then replaces application_token_enc with the attacker-supplied auth[application_token] without comparing to the stored value. Combined with ONAPPUNINSTALL, a non-admin employee can wipe the portal's cache and stop sync — violating brief rule 5 (reject anything that does not match) and causing loss of cached call data (rule 7 triggered by a forged event).

**Failure:** Manager-level user U on portal P copies access_token T from BX24.getAuth(). U POSTs /events/ event=ONAPPUPDATE, auth[member_id]=P, auth[access_token]=T, auth[application_token]=ATTACK. Backend calls app.info at P's stored client_endpoint with T → 200 → stores ATTACK as application_token_enc. U then POSTs event=ONAPPUNINSTALL, auth[member_id]=P, auth[application_token]=ATTACK → constant-time compare matches → status=uninstalled, access/refresh tokens wiped, purge_pending=true; the worker deletes every cached call for P; admins get 401 portal_inactive until someone reinstalls and re-backfills 500k rows.

**Fix:** For ONAPPUPDATE/ONAPPINSTALL/ONAPPUSERREADY on a known portal require BOTH: (1) auth[access_token] verified at the stored client_endpoint with user.admin=true (real lifecycle events carry the installer/admin auth), and (2) if a stored application_token exists, accept the new one only when the event token is admin-verified; log and refuse otherwise. Additionally make the dl.bitrix24.com/webhook/app-world.json source-IP allowlist mandatory (not optional) for /events/, and never accept a token-bearing event whose auth[member_id] differs from the OAuth-verified member_id of that token. Add tests: ONAPPUPDATE with a non-admin token must not change application_token_enc; subsequent ONAPPUNINSTALL with the attacker value must return 403.

## [MAJOR] Sync credential seeding from unproven-admin tokens (§4.9 rule 2 re-seed, rule 3 unknown-portal path)
ONAPPUPDATE re-seeds portal tokens when token_status != 'ok', and token-bearing events on an unknown portal create an ACTIVE portal row with the event's tokens as the sync credential. Neither path checks user.admin for the token owner. A non-admin's tokens become the worker's credential; voximplant.statistic.get with an 'own calls' user returns HTTP 200 with only that user's rows, so the cache is silently partial and, because token_status stays 'ok' and token_user_id != admin, the §4.4 step-6 admin open never re-seeds.

**Failure:** Portal P's installer token chain dies (token_status=reauth_required). Employee U (Manager role, own-calls right) forges ONAPPUPDATE with their own tokens (passes the app.info check). Backend stores U's tokens, token_status='ok', next_run_at=now(). Backfill runs and imports only U's calls; the admin opens the dashboard and sees a full-looking but wrong dataset ('total calls: 312' instead of 250,000) for as long as U's refresh chain lives (180 days); nothing flags it because no error occurred.

**Fix:** Any code path that writes access_token_enc/refresh_token_enc as the portal credential must first prove user.admin=true with that token at the OAuth-derived client_endpoint (batch user.current + user.admin), record token_user_id and an is_admin flag, and refuse otherwise (log portal_events(event_rejected)). Rule-3 unknown-portal events from non-admin tokens create no row. Also have the worker verify user.admin on the sync token once per day and flip token_status to 'no_stats_permission'/'reauth_required' if it becomes false.

## [MAJOR] Bearer JWT leaked through the 303 Location header into Caddy access logs (§4.4 step 8, §4.6)
The session JWT is handed to the SPA as `#s=<jwt>` in the Location header of a 303. The fragment never reaches the web server on the follow-up GET, but the Location header itself is a response header of the /app/ request, and Caddy's JSON access log records resp_headers (its built-in credential redaction covers Authorization/Cookie only, not Location). Every open of every tenant writes a valid 1-hour bearer token for that tenant into host logs.

**Failure:** Admin of portal A opens the dashboard. Caddy logs {"request":{"uri":"/app/?DOMAIN=a.bitrix24.kz..."},"resp_headers":{"Location":["/dashboard?d=a.bitrix24.kz&p=1&l=ru#s=eyJhbGciOiJIUzI1NiJ9..."]}}. Anyone with read access to the Caddy log stream (log shipping, a shared ops box, a backup of /var/log) replays `Authorization: Bearer <jwt>` against /api/v1/calls and reads portal A's full call history (acc=all) for up to 60 minutes, for every portal, continuously.

**Fix:** Do not put the JWT in a response header at all: return a small HTML page (already planned as the fragment fallback) that sets location.replace(url + '#s=' + jwt) from an inline script, or POST-message it into the SPA. Additionally, in docker/Caddyfile.snippet add a log filter that deletes resp_headers>Location (and keep request Authorization redaction on), and set Cache-Control: no-store on the handler responses. Add a test asserting no response header of /app/ contains the JWT.

## [MAJOR] Secrets in process logs — httpx INFO request lines (§6 logging, bitrix/oauth.py, bitrix/client.py)
The refresh exchange is a GET with client_secret and refresh_token as query parameters, and REST calls carry the access token as `auth=` in the URL or body. httpx's own logger emits 'HTTP Request: GET <full URL with query> "HTTP/1.1 200 OK"' at INFO level by default. The design's redaction is described for rest_log rows (key-based JSON redaction), not for third-party logger output, so with LOG_LEVEL=INFO the client secret and every tenant's refresh/access tokens land in container stdout, which Docker keeps for 5×50 MB and any log shipper forwards.

**Failure:** LOG_LEVEL=INFO in production. Worker refreshes portal P's token. stdout receives: HTTP Request: GET https://oauth.bitrix.info/oauth/token/?grant_type=refresh_token&client_id=texnobus.callanalytics&client_secret=<SECRET>&refresh_token=<R1> "HTTP/1.1 200 OK". `docker logs worker` now contains the app's client_secret (which lets anyone mint tokens for any portal via any leaked refresh token) and P's live refresh token.

**Fix:** In app/logging.py set the `httpx` and `httpcore` loggers to WARNING (or attach the redaction filter to the root handler with regexes for client_secret=, refresh_token=, access_token=, auth=), send the OAuth refresh parameters and REST `auth` in the request body rather than the query string wherever Bitrix24 accepts it, and add a test that captures logging output during a mocked refresh and asserts none of the secret values appear.

## [MAJOR] FORCE RLS + control-session jobs: purge_portal silently deletes nothing (§5.9, §3 policies)
calls/employees/crm_contexts have FORCED RLS with USING predicate on app.portal_id; the runtime role cannot bypass it. §5.9 describes purge_portal as `DELETE FROM calls WHERE portal_id = X AND id IN (...) LIMIT 10000` looping 'until none', but the tick and purge run in the control session with no app.portal_id set. Under RLS the DELETE affects 0 rows without any error, so the loop terminates immediately and clears purge_pending — brief rule 7 ('delete its cached call rows') is violated while the audit says purge_done. The same hazard hits the sync upsert if a commit inside the batch loop resets the SET LOCAL context (INSERT then fails WITH CHECK, or SELECT-based cursors return nothing).

**Failure:** Portal P uninstalls; ONAPPUNINSTALL sets purge_pending=true. tick() picks P, purge_portal runs DELETE ... in a control_session → 0 rows → 'none left' → purge_pending=false, portal_events(purge_done). 250,000 rows of P's call metadata (phone numbers, employees, CRM ids) remain in the database indefinitely; the portal is uninstalled so no one ever notices until a support engineer or an auditor queries as ca_owner. If P reinstalls, head_fetch/backfill re-upsert over the stale rows, but rows that Bitrix24 has since deleted stay visible.

**Fix:** Run purge_portal (and every job touching customer tables) inside tenant_session(portal_id) with SET LOCAL app.portal_id re-issued at the start of EVERY transaction (make tenant_session yield one transaction and open a new one per chunk). After the purge loop, verify with `SELECT count(*)` under the same context (must be 0) before clearing purge_pending, and raise if the first DELETE reported 0 rows while rows exist. Add tests: purge with rows present deletes them; upsert loop with 3 committed chunks keeps writing under the same portal context.

## [MAJOR] Recording playback modes vs. Bitrix24 'listen to recordings' right and credential-bearing URLs (§9, api/record.py, decision 17)
RECORDING_MODE=proxy is planned to stream with the portal (admin) token as one option, and RECORDING_MODE=redirect 302s the browser to the raw CALL_RECORD_URL. 'Call Recording: Listen' is a separate Bitrix24 permission from 'Call statistics'; proxying with the portal token lets a user with acc=own hear recordings Bitrix24 would refuse them, and the design's 'treat 403/404 as unavailable for your account' never fires because Bitrix24 sees the admin. Separately, if CALL_RECORD_URL is a download.json?auth=<token>&token=disk|... style link (the only documented recording link format), storing it plaintext and redirecting to it hands the portal access token to the browser.

**Failure:** Portal P sets Manager role = statistics 'own calls', recording listen = 'no access'. Employee U opens the dashboard (acc=own), clicks play on one of their own calls. GET /api/v1/calls/{id}/record in proxy mode fetches the recording with P's stored admin token → 200 → U listens to a recording their Bitrix24 rights forbid. In redirect mode with an auth-bearing URL, U's browser receives Location: https://p.bitrix24.kz/rest/download.json?auth=<admin access token>... and U now holds the admin token for an hour (crm scope: full CRM read).

**Fix:** Constrain the spike outcome in the design now: for non-admin viewers the proxy may use only the viewer's own token (fresh from BX24.getAuth(), verified via user.current, same sub as the JWT); the portal token is never used for a non-admin's playback. Never return call_record_url to the client and disable `redirect` mode unless the spike proves the URL carries no credential and enforces the listener's rights server-side; treat call_record_url as a secret in rest_log redaction (already partly covered by `auth=` stripping).

## [MAJOR] Domain rename deadlock (§4.4 step 4, §5.8, portals.client_endpoint)
client_endpoint is only ever updated from an OAuth refresh response, and a refresh is only triggered by expired_token or imminent expiry. When the portal address changes (or a custom domain is connected and the old one stops answering), user verification at the stale client_endpoint fails with a transport/HTTP error that is not expired_token, so no path re-learns the endpoint: opens are routed to /state/retry and the worker counts transport failures, pauses 6 h after 10, and never refreshes.

**Failure:** Portal renames from old.bitrix24.kz to new.bitrix24.kz; old host returns NXDOMAIN/404 the next day. Admin opens the app: POST /app/ carries DOMAIN=new.bitrix24.kz, but step 4 calls https://old.bitrix24.kz/rest/batch → connection error → 'Please reopen the app' forever. Worker: same host → consecutive_failures reaches 10 → 6 h pause, repeat indefinitely. Step-6 re-seed (which would fetch the new client_endpoint from OAuth) is never reached because it sits after step 4. The tenant is permanently broken with no self-service recovery.

**Fix:** In /app/: if the step-4 batch fails at the transport level (or the POSTed DOMAIN host differs from the client_endpoint host and the batch fails), run the refresh exchange with the POSTed REFRESH_ID, require response member_id == stored, take client_endpoint from the response (and update domain, portal_events(domain_changed)), then retry step 4 once. In the worker, on N consecutive transport failures perform one refresh under the single-flight lock to re-learn client_endpoint before pausing. Add a test with a mocked dead old host.

## [MAJOR] Token re-seed on every installer open (§4.4 step 6) — excessive refresh and unspecified failure path
Step 6 re-seeds the portal credential whenever token_user_id == me.ID, i.e. every time the installing admin opens the dashboard or any CRM tab, each time performing a refresh exchange. Bitrix24 documents that refreshing on a schedule or excessively can get the app blocked, and the design elsewhere says 'never on a schedule'. The failure branch (invalid_grant on the POSTed REFRESH_ID, OAuth timeout) is not specified; if it sets token_status='reauth_required' or next_run_at='infinity', a healthy worker chain is killed by a benign open. §4.3 step 4 also does not list token_status among the columns the install upsert resets, so a reinstall after 'reauth_required' can leave the tick filter (token_status='ok') excluding the portal.

**Failure:** Installer admin works in CRM all day, opening 60 deal cards with the Calls tab → 60 refresh exchanges at oauth.bitrix.info for one portal, each rotating a token pair while the worker may be mid-batch with the previous access token (worker gets expired_token, takes the FOR UPDATE lock, waits behind the open's lock). If one exchange returns invalid_grant (Bitrix24 POSTed a REFRESH_ID from a chain we already rotated) and the code maps OAuth invalid_grant to reauth_required as §5.8 does, sync stops until the next open — and the dashboard flips between 'sync blocked' and running.

**Fix:** Re-seed only when the chain is actually dead (token_status != 'ok'), when token_refreshed_at is older than a threshold (e.g. 30 days) or when the token owner differs and the opener is an admin choosing 'take over' on the settings page; never on a routine open. On a failed opportunistic re-seed keep the existing credential untouched and only log portal_events(refresh_failed). Make the /install/ upsert explicitly set token_status='ok' (or 'method_missing') and reset next_run_at. Add a test: two admin opens within 5 minutes cause zero OAuth calls when the chain is healthy.

## [MINOR] crm_contexts reuse across users when CRM resolution fails (§4.4 step 4/7, §4.8)
crm_contexts is keyed per portal, not per user, and 'refreshed on every tab open with the opener's token'. If the opener's crm.deal.get / crm.activity.list commands error (no CRM rights) the design does not say the open fails; if the handler still mints a JWT with ent={DEAL,id}, reads fall back to the row resolved earlier by a user who does have rights.

**Failure:** Manager U2 has no access to deal 5. U2 forges POST /app/ with PLACEMENT=CRM_DEAL_DETAIL_TAB, PLACEMENT_OPTIONS={"ID":"5"} using their own AUTH_ID. Batch: crm.deal.get → ACCESS_DENIED in result_error, but the handler proceeds and issues a JWT with ent={DEAL,5}. GET /calls uses the crm_contexts row resolved yesterday by admin U1 (contact ids, 300 activity ids) and returns U2's own calls that touch those contacts, revealing which of the deal's contacts U2 has phoned (scope_filter limits it to own rows, so the leak is the contact→deal association, not other users' calls).

**Fix:** If any CRM command of the step-4 batch returns an error for a CRM tab, redirect to a translated state ('no access to this CRM item') and do not mint an entity JWT; only overwrite/serve crm_contexts from a successful resolution by the current opener, and store resolved_by_user_id checks (row must be fresher than the JWT iat or resolved by the same sub) in calls_repo.

## [MINOR] Delayed or retried ONAPPUNINSTALL after a reinstall (§4.9 rule 1)
application_token_enc is kept across uninstall so late duplicates verify, and reinstall replaces it only if Bitrix24 issues a new value. Bitrix24 retries event delivery on non-2xx; a retry that arrives after a quick reinstall passes the compare and wipes the new installation. The event's `ts` field is ignored.

**Failure:** ONAPPUNINSTALL for P arrives during an api deploy → 502 → Bitrix24 queues a retry. Admin reinstalls P two minutes later (install_completed_at=T). The retry arrives at T+3 min with the same application_token → status=uninstalled, tokens wiped, purge_pending=true → the fresh head_fetch data is deleted and admins get portal_inactive until another reinstall.

**Fix:** Ignore (200, logged) any ONAPPUNINSTALL whose `ts` is earlier than portals.install_completed_at, and record the last processed event ts per portal for idempotency.

## [MINOR] Redaction coverage of inbound/outbound bodies (§6, ONAPPUSERREADY, session/exchange, reauthorize)
The redaction list is a fixed set of keys (AUTH_ID, REFRESH_ID, APPLICATION_TOKEN, auth, access_token, refresh_token, client_secret). ONAPPUSERREADY carries the system user's long-lived tokens under data[...] with keys not enumerated in the design; the refresh-response body and the JSON bodies of POST /api/v1/session/exchange and /portal/reauthorize (raw user access/refresh tokens) are not covered by 'rest_log' redaction at all if a generic exception handler or middleware logs request bodies.

**Failure:** ONAPPUSERREADY arrives with data[access_token]/data[refresh_token] (or differently named keys); rest_log.request stores auth[*] as [redacted] but data{} verbatim → the system user's 180-day refresh token sits in plaintext in rest_log for 7 days. Similarly a 500 in /api/v1/portal/reauthorize with a body-logging exception handler prints the admin's refresh token to stdout.

**Fix:** Implement redaction as a recursive walk over every dict/list that masks any key matching /(token|secret|auth|password|AUTH_ID|REFRESH_ID)/i regardless of nesting, apply it to both request and response bodies before every rest_log insert, mark data{} of ONAPPUSERREADY as fully redacted, and ensure the FastAPI exception handler never logs bodies for /api/v1/session/exchange and /api/v1/portal/reauthorize. Add a test feeding a nested payload and asserting no token substring survives.

## [MINOR] Unauthenticated triggers of OAuth refresh exchanges (§4.3 step 2, §4.4 step 2, §4.9 rule 3)
/install/, the /app/ self-heal path and the unknown-portal event path each perform a refresh exchange before any admin check, driven by any REFRESH_ID the caller supplies. Any employee can obtain unlimited fresh pairs via BX24.refreshAuth() in the iframe and script these endpoints, generating a high volume of refresh calls (and invalid_grant failures) attributed to the app's client_id.

**Failure:** A disgruntled employee of portal P loops: refreshAuth() → POST /install/ with member_id=P and the new REFRESH_ID, 5 times per second. The backend performs 5 refresh exchanges per second at oauth.bitrix.info for hours; Bitrix24's 'excessive refresh gets the app blocked' rule triggers against texnobus.callanalytics for all tenants; every exchange also rotates a pair and each non-admin result is discarded.

**Fix:** Rate-limit refresh exchanges per member_id and per source IP (e.g. 5 per 10 minutes) in front of these three paths; for /install/ and self-heal on an already-active portal, verify AUTH_ID at the stored client_endpoint and check user.admin BEFORE any refresh exchange, and only exchange the refresh token when the caller is an admin or the portal is unknown/uninstalled.

# Critique 3

**Verdict:** The cursor foundations are right: using the statistics ID (not CALL_START_DATE) for head/incremental/backfill removes the equal-timestamp page-boundary problem, the timezone-offset problem and the backdated-row problem, and (portal_id, ID) is the correct upsert key over CALL_ID/SESSION_ID. Committing rows and cursor together makes a plain crash safe. The design breaks, however, on partial failures inside a batch (one failed command silently and permanently drops a page — blocker), on any single unparsable/constraint-violating row (cursor pinned forever), on a crash between the two head_fetch steps, on stale workers with no write fencing (leftover rows after uninstall purge), on an under-specified purge that forced RLS turns into a silent no-op, and on 429/503 accounting that can throttle or pause a busy portal for hours. Fix the contiguous-prefix cursor rule, per-row quarantine, head-state idempotency, lease/generation fencing and the tenant-session purge before milestone 1's sync work; the rest are polish.

## [BLOCKER] sync/head_fetch + backfill: per-command failure inside a batch
head_fetch and backfill issue 10–50 offset pages in one batch (halt=0) and then set `low_id = min(ID seen)` / `high_id = M` over whatever pages came back. Nothing says the cursor may only advance through the *contiguous prefix* of successful pages. A single failed command in the middle (INTERNAL_SERVER_ERROR, ERROR_UNEXPECTED_ANSWER, a per-command OPERATION_TIME_LIMIT) leaves a 50-row hole that no later job ever revisits: backfill continues strictly below low_id, incremental strictly above high_id, and the 72 h rescan only covers rows with a recent call_start_date.

**Failure:** Install on a 500k-row portal. head_fetch batch: commands 0–19 OK, command 20 (start=1000) returns result_error INTERNAL_SERVER_ERROR, commands 21–49 OK. Worker upserts 2,450 rows, sets high_id=M, low_id=min(seen)=M-2499, backfill_status='running'. The 50 calls at positions 1000–1049 (from ~yesterday, the ones the moderator scrolls to) are never fetched again: backfill uses `<low_id`, incremental `>high_id`, rescan starts at from_id = min(bx_id) with recent start date, which is *below* the hole only by luck and, being ID-based, is skipped once the hole ages out. Same for a backfill batch: a hole of up to 50 rows per failed command, permanently.

**Fix:** Rule: a batch's cursor may advance only across the longest prefix of commands with no error; rows from pages after the first failed page are discarded (or the whole batch is retried). For head_fetch, treat any per-command error as 'head_fetch failed, stay pending, retry'. Add a test in test_cursor.py: batch with page k failing must leave low_id/high_id at page k-1's boundary.

## [MAJOR] sync/upsert: poison rows stall the cursor forever
CHECK constraints on Bitrix-supplied enums (`call_type BETWEEN 1 AND 5`, `crm_entity_type IN ('CONTACT','COMPANY','LEAD')`), `call_start_date NOT NULL`, and narrow varchar widths (call_failed_code 16, phone_number 64, call_id 128) make the 2,500-row batch transaction fail on a single unexpected row. Because rows and cursor commit together, the cursor never advances; the visit records a failure, and after 10 attempts the portal pauses 6 h and repeats the same failing batch forever. Also unspecified: head_fetch step 1 (50 rows) and step 2 page 0 return the same rows — upserting both in one statement raises 'ON CONFLICT DO UPDATE command cannot affect row a second time'.

**Failure:** A portal with an external REST telephony line returns one row with CRM_ENTITY_TYPE='DEAL' (or a new CALL_TYPE 6, or an empty CALL_START_DATE from a malformed externalCall.register). The backfill batch containing that row violates the CHECK, rolls back, low_id does not move; every subsequent visit re-fetches the same batch, fails, consecutive_failures reaches 10, portal pauses 6 h, repeats. Every call older than that row is never imported and the settings page shows the same error forever.

**Fix:** Drop CHECK constraints on external enums (store raw strings/ints; map in the UI), make call_start_date nullable-with-fallback or quarantine the row, widen strings to text, dedupe rows by bx_id inside a chunk before INSERT, and quarantine per row: parse each row independently, skip + log rows that fail parsing (count in portal_sync.last_error_text), never let one row block cursor progress. Add a test with a fixture page containing one unparsable row.

## [MAJOR] sync/head_fetch state machine resumability
backfill_status goes pending -> head -> running, but head_fetch is described as running only when 'pending'. If the 'head' transition (and high_id=M from step 1) is committed before the step-2 batch commits and the worker dies, the portal is stuck in 'head': head_fetch does not run (not pending), backfill does not run (not running), incremental sees nothing above M.

**Failure:** Worker OOM-killed between head_fetch step 1 (commits backfill_status='head', high_id=M, backfill_total) and step 2. Next tick: lease expired -> consecutive_failures++, sync_portal runs incremental `>M` (only calls after install) and skips backfill. Dashboard shows only calls made after install, forever; 'Importing history 0 / 250 000' never moves.

**Fix:** Make head_fetch idempotent and run it whenever backfill_status IN ('pending','head'); or do not persist 'head' at all and commit step 1 and step 2 in one transaction. Add a crash-between-steps case to test_cursor.py.

## [MAJOR] worker fencing: stale runner after lease loss or uninstall
Nothing fences portal_sync/calls writes to the current lease holder. A worker whose lease expired (HTTP hang longer than 5 min — no REST timeout is specified, only 15 s for OAuth) or whose portal was uninstalled mid-visit keeps committing: it can re-insert rows after purge_portal finished and clobber the cursor reset done by the uninstall handler.

**Failure:** Portal A backfilling; ONAPPUNINSTALL arrives: handler sets status='uninstalled', purge_pending=true, resets cursors, clears the lease. Tick (b) starts purge_portal and deletes all rows in 10k chunks, finds none left, sets purge_pending=false, logs purge_done. Meanwhile the still-running worker's in-flight batch (issued before revocation) returns 2,500 rows; the worker upserts them and commits low_id. Result: 2,500 call rows of an uninstalled customer remain in `calls` indefinitely (rule 7 violated); on reinstall, purge_pending is false so they are not re-purged. Same mechanism lets a stalled worker overwrite the cursor of a newer runner.

**Fix:** Add a `sync_generation` (or reuse token_version) bumped by uninstall/reinstall/install and stored in the lease; every upsert/cursor transaction must include `UPDATE portal_sync ... WHERE portal_id=:pid AND lease_owner=:me AND lease_expires_at>now() AND sync_generation=:gen` and abort if 0 rows; also `SELECT status='active' AND NOT purge_pending` inside the same transaction. Set an httpx timeout (e.g. 120 s) well below the 5-min lease. purge_portal should loop until a final `NOT EXISTS` check under a fresh transaction.

## [MAJOR] purge_portal and forced RLS
Forced RLS with `app.portal_id` unset yields zero rows (fail-closed). purge_portal is dispatched from tick(), which runs in the control session; the design never states that purge_portal opens tenant_session(portal_id). If it runs in the control session, `DELETE ... LIMIT 10000` deletes 0 rows, the loop ends immediately, purge_pending is cleared and `purge_done` is logged — silently retaining all of the uninstalled portal's data.

**Failure:** ONAPPUNINSTALL for a 300k-row portal; tick(b) -> purge_portal(pid) using control_session(); DELETE affects 0 rows (policy predicate NULL); code interprets 'no more rows' as finished; purge_pending=false, portal_events(purge_done). 300k rows, employees and crm_contexts stay forever; no error anywhere.

**Fix:** Specify purge_portal runs inside tenant_session(portal_id); assert the first DELETE affects >0 rows when a pre-count (in the same tenant session) was >0; add a test that runs purge as ca_app and verifies emptiness as ca_owner (BYPASSRLS) — this is the only role that can see cross-tenant leftovers.

## [MAJOR] throttle: 429 OPERATION_TIME_LIMIT and QUERY_LIMIT_EXCEEDED handling
Two defects: (1) on 429 the design writes `capabilities.operating_limit_s = last observed operating`. The limit is per account+method and the block applies to all apps of that account, so a 429 caused by another app (or observed early in our own ramp) records a tiny limit, and the soft ratio then throttles this portal permanently. (2) 503/429 do `consecutive_failures++`, and the 10-failure rule pauses the portal 6 h; `next_run_at = operating_reset_at + 5 s` only frees one 1-minute basket, so a heavy backfill legitimately sees several 429s in a row.

**Failure:** (1) Another Market app on the same portal hammers voximplant.statistic.get; our first 50-command batch gets 429 while our last successful time.operating was 18 s. capabilities.operating_limit_s=18 -> soft limit 14 s -> one 50-page batch (~15 s) trips it every visit -> backfill of 500k rows crawls at one batch per 10 min (~33 h) with no way back because the value is never raised. (2) Our own backfill hits 384 s soft/480 s hard; after reset_at+5 s only ~48 s drained; the next batch gets 429 again; repeat 10 times -> consecutive_failures=10 -> 6 h pause; the pattern recurs each cycle.

**Fix:** Floor the adaptive limit (never below 300 s), decay it back toward the default after N clean windows, and only lower it when *our* observed operating is close to the limit. Exclude 429/503 from the consecutive-failure breaker (track them in a separate throttle counter). On 429 wait max(operating_reset_at, now()+ (operating - 0.5*limit)/… ) or simply reset_at + 60 s and halve batch_pages.

## [MAJOR] calls.call_record_url storage and late-update churn
CALL_RECORD_URL is stored verbatim in plaintext and diffed in the upsert. Its real format is an open question; the closest documented analogue (disk DOWNLOAD_URL) embeds `auth=<access_token>` of the caller — here the installing admin's portal token. If so: (a) the cached URL carries a privileged credential per row, (b) `RECORDING_MODE=redirect` would 302 any user to it, (c) a per-read token makes every rescan mark all 6,000 rows as `content_changed_at` and rewrite them hourly, and (d) the URL is dead after the next refresh (≤1 h) so the cache value is useless anyway.

**Failure:** Spike finds CALL_RECORD_URL = https://portal.bitrix24.kz/rest/download.json?auth=<installer access token>&token=disk|... . Backfill stores 200k such URLs; hourly rescan rewrites all 72-h rows because the auth token rotated; an operator later flips RECORDING_MODE=redirect: every 'own'-scope employee receives a 302 to a URL containing the admin's live access token, usable for any REST call for up to an hour.

**Fix:** In statistic.py normalise the URL: strip `auth`/token-bearing query params (store `record_url_host_path` + a `record_url_kind` flag), exclude the volatile URL from the IS DISTINCT FROM comparison, and hard-forbid `redirect` when the stored value ever carried credentials (only `proxy` with a per-request token). Make this part of the spike's capture step so the schema is right before backfill fills 500k rows.

## [MINOR] rescan lower bound derivation
`from_id = min(bx_id) WHERE call_start_date >= now() - 72h` is NULL for a portal with no calls in 72 h (small portals every weekend). If NULL reaches the filter (`">=ID": null`) Bitrix ignores it and the hourly rescan re-reads the whole history.

**Failure:** 20-employee portal, Friday evening to Monday: no calls. Sunday 03:00 rescan computes from_id NULL, sends FILTER {">=ID": null} SORT ID ASC in 50-page batches, follows `next`, and pages through all 120k rows (2,400 commands) — every hour until Monday — burning the operating budget and blocking backfill on a reinstalled portal.

**Fix:** Keep `rescan_from_id` as a column: set it to `high_id` recorded ~72 h ago (store high_id with a timestamp each incremental run, or persist last_rescan_from_id and advance it monotonically). Skip the rescan when no rows fall in the window.

## [MINOR] /install/ re-run on an active portal
/install/ step 4 always resets portal_sync (high_id=0, low_id=NULL, pending). Bitrix opens the install URL again on app version updates and any admin can re-trigger it; the whole history is then re-imported although the cache is complete.

**Failure:** Version 2 published; a 500k-row portal updates; /install/ resets cursors; head_fetch + backfill re-fetch 500k rows over ~2 h, the dashboard shows 'Importing history 2 500 / 500 000' banner again, and a concurrently running worker for that portal writes its stale cursor back over the reset.

**Fix:** On an already-active portal (status='active', install_completed_at set) refresh tokens/placements/application_token only and leave portal_sync untouched; reset cursors only when status was 'uninstalled' or the portal row is new.

## [MINOR] incremental batch sizing
Incremental issues `batch_pages` (up to 50) blind offset commands `>high_id` every 5 min even when only a handful of new rows exist; 49 empty commands each run a filtered COUNT and query, all counted toward the per-method operating time.

**Failure:** Portal with 7 new calls per 5 min: 2 incremental runs per 10-min window × 49 empty commands × ~0.2 s ≈ 20 s of the 384 s soft budget wasted, slowing backfill and pushing the throttle earlier; on 200 portals it is 200× that against one source IP for nothing.

**Fix:** Send one command first; use its `total`/`next` to decide how many further pages to pack into the next batch (min(ceil(total/50), batch_pages)).

## [MINOR] filter-honoured guard on cursor queries
The whole cursor scheme assumes Bitrix honours `>ID` / `<ID` / `>=ID` on voximplant.statistic.get (verified in docs but never validated at runtime, and on-premise builds lag). If a build ignores the operator, incremental returns the first pages of the full history, `high_id = max(ID seen)` does not move, and 'if the last command still had next, repeat immediately' becomes a hot loop.

**Failure:** On-premise 22.x box ignores the `>` prefix: every incremental run re-reads IDs 1..2500, high_id stays at 2500 < M, `next` is present, the loop repeats immediately (paced at 2 req/s) until the operating limit blocks the method for the whole account, including Bitrix's own telephony UI users of that app.

**Fix:** Assert every returned row satisfies the filter it was requested with (ID > high_id, ID < low_id, ID <= M); on violation set token_status='method_missing'-style terminal state (`filter_unsupported`), log, stop. Cap 'repeat immediately' iterations per visit.

## [MINOR] rest_log durability vs. moderation requirement
rest_log rows are written 'inside the same transaction as the work'. When the work fails (constraint violation, deadlock, serialization error) the transaction rolls back and the REST request/response record is lost — exactly the calls a support engineer needs and the moderation rule expects to be kept.

**Failure:** Backfill batch response received (2,500 rows), upsert raises (see poison-row issue), rollback: no rest_log row for that batch; the portal's settings page shows 'INTERNAL error' with nothing in the log for the failing request.

**Fix:** Write rest_log in its own short autocommit transaction (or on the except path before re-raising); keep correlation_id to tie it to the failed work.

## [MINOR] dashboard aggregation indexes on 500k-row portals
All dashboard aggregations use `calls_portal_start_idx (portal_id, call_start_date DESC)` then heap-fetch every row for the period; summary, per-day, hour×weekday and per-employee are separate queries, so an admin 'all time' view scans the full cache four times.

**Failure:** 500k-row portal, admin picks custom period = 2 years: four queries × 500k heap tuples ≈ 1–3 s per dashboard load; with the 5-minute-interval upsert traffic and a few concurrent viewers the API container becomes the bottleneck during moderation.

**Fix:** Make the range index covering: `(portal_id, call_start_date DESC) INCLUDE (portal_user_id, call_type, result_group, call_duration, rest_app_id, has_record)` for index-only scans, and compute summary + per-day + heatmap in one query with GROUPING SETS. Cap custom period at e.g. 366 days in v1.

## [MINOR] jobs/apscheduler dispatch and lease-expiry accounting
tick() leases up to GLOBAL_PORTAL_CONCURRENCY portals and 'dispatches' sync_portal, and every job has max_instances=1. If sync_portal is one APScheduler job id, extra dispatches are dropped; if tick awaits them inline, ticks misfire during a 20-batch visit. Either way leased portals sit idle for 5 min and are then charged `consecutive_failures++ / lease_expired` as if they crashed.

**Failure:** 4 free slots, tick leases portals A–D and calls run_now('sync_portal') four times; APScheduler runs A and logs 'maximum number of running instances reached' for B–D. B–D stay leased and untouched for 5 min, then each tick counts a phantom crash; after ten such cycles they pause 6 h.

**Fix:** Dispatch inside the worker with asyncio.create_task under a Semaphore(GLOBAL_PORTAL_CONCURRENCY); tick must never await sync work; if APScheduler jobs are used, id them `sync_portal:{portal_id}`. Do not increment consecutive_failures on lease expiry unless a run actually started (record run_started_at).
